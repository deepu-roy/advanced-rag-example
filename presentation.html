Section 1 · Environments

GitHub Codespaces & Devcontainers

Every lab in this repo runs the same way for every participant, on any laptop, with zero "it works on my machine" debugging — because nobody's machine is involved.

The old way

Local setup, every time

Install Python 3.12, create a venv, fight a FAISS wheel that won't build on Apple Silicon, discover you have the wrong CUDA driver, realize your Python is actually 3.9 because of an old .zshrc alias — twenty minutes before anyone's written a line of the actual lab.

With Codespaces

One click, identical environment

The repo declares its environment in .devcontainer/. GitHub builds that exact environment in the cloud and hands you a VS Code (or terminal) already inside it. Every participant gets byte-for-byte the same Python, the same models pre-downloaded, the same Ollama server already running.

What is a devcontainer, exactly?

Section 1, continued · Features & benefits

What's possible, and why it matters here

What's possible

Prebuilds

GitHub builds the container ahead of time, so launch is seconds, not minutes.

Any client

Browser, desktop VS Code, JetBrains Gateway, or the gh cs CLI over SSH.

Port forwarding

A server running on localhost:11434 in the cloud is reachable from your laptop's browser.

Secrets

Org- or user-level encrypted secrets injected as env vars — an API key never touches the repo.

Machine sizes

2 to 32 cores, picked per-repo or per-launch, including larger-RAM and GPU-enabled options.

Disposable

Break something? Delete the Codespace, spin up a fresh one from the same recipe in a minute.

Why it matters here

  • Zero setup time. A 90-minute workshop doesn't lose 20 of them to pip errors.
  • Identical bugs. If something breaks, it breaks the same way for everyone — easy to debug together.
  • Sandboxed. Nobody installs anything on their own laptop; nothing to clean up afterward.
  • Version-controlled environment. The devcontainer config lives in git — it reviews and evolves like code.
  • Same recipe, real production skill. Writing a devcontainer is directly useful back at work, not a workshop-only trick.

Section 1, continued · Where this actually gets used

Real-world use cases, not just workshops

This lab is one use case. Teams run on Codespaces (or a local devcontainer running the exact same config) for reasons that have nothing to do with training.

🚀 Instant onboarding

A new hire opens a PR on day one instead of spending day one fighting a Python version manager. The environment is the same one everyone on the team already uses.

🌍 Frictionless OSS contribution

A contributor fixing a typo shouldn't need to install your entire build toolchain. A "Contribute" badge that opens a working Codespace turns a 10-minute favor into a 10-minute favor, instead of a 45-minute yak-shave.

🔎 Ephemeral PR review

Spin up a live, running instance of exactly the branch under review, click through the actual UI change, then delete it. No more reviewing a frontend PR by reading a diff and hoping.

🎓 Workshops & training

This lab. Every participant starts from an identical, pre-warmed environment in under a minute — the facilitator debugs one broken laptop instead of twenty.

🗄️ Legacy & conflicting toolchains

Maintain a 2019 service pinned to Node 12 and today's service on Node 22 without version managers fighting each other on your actual laptop.

🤝 Live demos & pair programming

Port-forward a running app straight from the cloud container into a teammate's or client's browser. No screen-share lag, no "works on my machine" during the demo itself.

Section 1, continued · The newest use case

Sandboxing autonomous AI coding agents

An agent that can run shell commands, install packages, and edit files shouldn't have your SSH keys, your other repositories, or your production credentials sitting within reach.

⚡ increasingly the default pattern for agentic coding tools

A bad instruction, a hallucinated command, or a compromised dependency shouldn't be able to touch anything real. Running the agent inside a disposable container solves this by construction: if it does something wrong, you delete the Codespace. Nothing on your actual machine was ever at risk.

This isn't hypothetical — it's how GitHub's own autonomous Copilot coding agent works today: given a GitHub Issue, it does its work inside an isolated, cloud-hosted sandbox (a GitHub Actions runner configured by your repo's own copilot-setup-steps.yml) and hands back a pull request — it never touches a human's machine at all. GitHub Copilot's interactive sessions now offer the same idea explicitly, with a /sandbox enable mode that restricts an agent's filesystem and network access before it runs a single command. The same principle applies however you're agentically coding — Claude Code, Copilot, Cursor, or anything else driving a shell — a devcontainer is a natural, standard place to put that boundary.

Section 2, continued · What it is, and isn't

What Simple RAG is — and is not

What it is

  • A way to give a language model relevant context it wasn't trained on — this week's runbook, not last year's Wikipedia dump.
  • Nearest-neighbor search in embedding space: turn text into vectors, find the closest ones.
  • Cheap, fast, and a genuinely strong baseline — most of this lab's own control queries never need anything more.

What it is not

not a fact database — it retrieves text that looks relevant, not verified truth.
not fine-tuning — the model's weights never change; only its input does.
not guaranteed correct — if the wrong chunk is retrieved, the model confidently answers from the wrong chunk.
not a replacement for a good corpus — garbage in, garbage retrieved.

Why it doesn't scale: a real failure from this repo

Ask Lab 1's naive dense retriever: "What's the process if a delivery isn't OTIF?" The document that actually answers this never uses the acronym "OTIF" — it spells out "on-time-in-full" throughout. Watch what gets ranked first instead.

Scores are real cosine similarities from solutions/lab01_simple_rag.py — nothing here is invented.

Why this happens:

Dense embeddings represent meaning, and "OTIF" — a rare acronym the model has little to anchor semantically — doesn't embed close to "on-time-in-full" in vector space. Meanwhile the company glossary document literally contains the string "OTIF" in a definition, which is enough surface similarity to outrank the actual runbook. This gets worse, not better, as a corpus grows: more documents mean more coincidental near-matches like this one. Section 3 fixes exactly this.

Section 4 · Two kinds of "relevant"

Hybrid Retrieval

Dense embeddings and classic keyword search (BM25) fail in almost opposite ways. Hybrid retrieval runs both and combines their rankings, so each one's blind spot is covered by the other's strength.

Dense (semantic) search

Great at: paraphrase, synonyms, "meaning" — finds "time off after a death in the family" even when the query says "bereavement".

Bad at: exact rare tokens. Three documents that all say "this reference lists the error codes for the ___ subsystem" look nearly identical in embedding space — the one distinguishing detail, a specific code, can get outweighed by shared boilerplate.

Sparse (BM25 / lexical) search

Great at: exact identifiers, codes, names — rare tokens get a high IDF weight, so a document containing the literal string "E-4021" wins decisively.

Bad at: paraphrase. It has no idea "bereavement" and "a death in the family" mean the same thing.

Section 4, continued · Where dense search breaks

Real failure: three near-identical documents

Query: "E-4021 cause". Three documents share almost all their framing language, differing only in which error codes they list.

Section 4, continued · Combining two rankings

Why Reciprocal Rank Fusion?

You can't just average a cosine similarity (0 to 1) with a BM25 score (0 to unbounded, corpus-size dependent) — they're not on the same scale. RRF sidesteps the whole problem by ignoring the scores entirely and fusing on rank position instead:

score(doc) = Σ over every ranking that contains it, of   1 / (k + rank(doc))

Section 4, continued · Try it yourself

Live fusion, with real rankings

Query: "E-4021 cause"

Try dragging k to 1 or 100 — low k lets a #1 finish dominate; high k flattens the effect of rank almost entirely. 60 is the conventional default because it works well across most corpora without tuning. Notice manifest and billing stay razor-close at every value of k — this document-level view is a simplification (the real lab code fuses individual chunks, not whole documents); the exact verified result from solutions/lab03_hybrid_rrf.py is 0.032266 vs 0.032258 — manifest wins, but only just. RRF got the right answer; it didn't get a confident one. That gap is exactly what Section 5 fixes.

Section 5 · Precision, not recall

Reranking

Hybrid retrieval is good at getting the right document somewhere in a top-20 pool. It's not always good at putting it first. Reranking's whole job is reordering a pool that's already been narrowed down — it's a precision tool, not a recall tool.

Bi-encoder vs. cross-encoder

Query and passage never "meet" until their two independent vectors are compared at the end. Fast — passage vectors are precomputed once for the whole corpus — but the encoder never sees them together.

Cross-encoder (reranking)

One joint encoder (full attention across both)

Query and passage are read together, token-by-token attention across both. Far more accurate at judging true relevance — but too slow to run over an entire corpus, which is why it only reranks an already-narrow pool.

Section 5, continued · Other options

Other reranking methods, briefly

LLM-as-reranker

Ask a general LLM to score or rank candidates directly (pointwise or listwise). Most flexible, most expensive per query.

ColBERT (late interaction)

Keeps one vector per token instead of one per passage, comparing token-to-token. A middle ground: more accurate than a bi-encoder, cheaper than a full cross-encoder.

Multi-vector / ensemble

Combine several rerankers' scores (or a reranker with the original fused score) with a weighted blend, when one signal alone isn't trusted enough.
